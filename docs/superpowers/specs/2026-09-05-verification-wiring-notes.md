## Authenticated core wiring

- Current public verification routes are apps/backend/src/routes/verification.routes.ts and the large verification.controller.ts. They currently create/select accounts and issue JWTs. Replace with small authenticated flow handlers/services; no eligibility handler may issueSession or select account from submitted studentEmail/phone/registration.
- New flow can use POST /verification/initiate for canonical university plus literal affirmative current processing notice, POST /verification/email/request and /email/confirm for account-bound challenges, POST /verification/registration for strict matched provider snapshot/application, GET /verification/status for own effective status, POST /verification/disclosures for separately approved merchant/origin/purpose, DELETE /verification/consents/:id for own withdrawal.
- Retire old public POST /email and GET /email/verify magic login grant with explicit410 upgrade guidance. Public registration cannot remain callable without authentication. Legacy /status/:studentId must require exact own subject or retire; no public status-by-ID data leak.
- WhatsApp/portal are not legitimate student assurance merely because a phone OTP/provider URL exists. Advertise only implemented configured methods. First working path is approved-email OTP. Retired unsupported routes should be explicit, and old unsafe Redis OTP helpers must not remain used by any live route.
- Signup request/confirm remain in auth.controller.ts at present. Preserve request payload claims but add challengeId and explicit processing action/notice version. Normalize account lookup consistently with030 unique lower(btrim(email)). Confirmation consumes challenge, rechecks pending claims and active policy, creates account/student, attaches real processing consent and mailbox/evidence, all in one transaction. Only then issue durable login session. If response/session issuance fails after account creation, ordinary login must recover; do not claim the account was rolled back after commit.
- Signup has no pre-existing user row to lock. The executable flow plan must explicitly reconcile its order with failed-guess persistence: do not insert a new account and then commit it merely to preserve an invalid-OTP budget increment. Lock/recheck policy, consume the normalized-mailbox signup challenge, commit only failed-attempt state on invalid proof, and insert the new identity only after successful consumption in that same transaction. New identity creation is the bounded exception to existing-subject user-first locking; unique normalized email plus the locked signup budget serializes competing confirmations. Never acquire an existing user's lock after the signup budget or reinterpret a duplicate account as permission to log in. Tests must demonstrate invalid guesses create no account and racing confirmations create exactly one account/proof/session authority.
- Generic student registration currently fails without university and is not a functioning personal-email onboarding path. Direct generic student form to dedicated signup rather than silently creating unverified personal-email enrollment policy. Personal-email/manual-review product remains separately unapproved.
- Public /auth/verify-student-email becomes informational approved-domain check only. Its UI must say domain supported/unsupported, never 'email found in university database'. Backend current student-email-verification.service.ts and legacy email-verification.service.ts must both defer to the one canonical policy, or dead routes/helpers must be removed/retired explicitly.
- Existing account/vendor email confirmation in auth.controller.ts stores plain OTP and marks the shared flag. Migrate separately to account_email challenge + mailbox-only proof; it must not grant student assurance. Frontend paths auth/vendor/verify-email and auth/student/verify-email use this API and require matching request/confirmation changes.
- Additional observed purpose issue: auth.controller.ts verifyResetOTP currently issues an access JWT with hardcoded student role. Track a separate bounded auth-purpose fix, not a silent change to A14. A password-reset grant must never pass ordinary access-token authentication; reset proof and password+session revocation must be atomic. Inspect reset UI hooks before choosing compatible transport.

## Strict provider adapter

- Current file is registration-lookup.service.ts, not registration-verification.service.ts. It infers success from returned name/studentData and trusts non-boolean verified, and fills a provider email from caller input. All three are prohibited.
- Parse one explicit versioned schema from an approved configured endpoint: true current enrollment, attested email, registration number, bounded validity; a matched explicit negative is distinct from unknown/outage. Do not use HTTP404 or arbitrary name as a negative/positive current-enrollment decision. Never fallback provider email to request email.
- Begin snapshot transaction -> external HTTP outside transaction -> revalidate/apply snapshot transaction. Existing context/profile/policy/grant generation determines whether result is stale. Source tag comes from trusted configured adapter, not arbitrary caller data.
- Real tests use only mock transport boundary; DB is real synthetic fixture. No real university/provider requests.

## Widget/browser boundary

- apps/web/src/app/widget/verify/page.tsx has no login gate and requests public registration/WhatsApp, then uses returned access JWT. Rewrite around signed-in account, server-provided email/current proof/notices and explicit separate merchant grant. Use apiClient for authenticated calls, publicApiClient only public bootstrap/preflight.
- apps/web/src/app/auth/student/register/page.tsx owns the entire two-stage flow; preserve safe same-origin redirect and context on submit/success/sign-in link. Login currently uses AuthContext getSafeStudentRedirect; signup link must carry it.
- AuthContext falls back to decoded JWT user when /auth/me fails. Do not treat this fallback as verified/current account state for the verification flow; its authenticated server calls must succeed. auth.ts storage functions currently throw when storage is blocked; wrap reads/clears and surface write failure, do not hide failed persistent login.
- Merchant allowlists currently use hostname in widget.controller.ts domainCheck, verification.controller widget-token and widget SDK api.js.030 adds empty allowed_origins. Replace through explicit operator configuration, no automatic conversion of host-only entries. Widget SDK should send actual window.location.origin, not a domain override used as authority.
- SDK files are apps/widget/src/widget.js, api.js, modal.js (plain JS, not TS). Existing handleMessage accepts only exact Awoof origin plus current iframe.contentWindow; preserve this and add per-flow nonce. Remove studentId/locally invented verifiedAt/method from every callback/postMessage response.
- Restricted iframe storage needs a functional top-level option, not an infinite sign-in loop: parent widget offers a user-clicked popup button, retains exact WindowProxy plus nonce, and accepts success only from that tracked popup or iframe with exact Awoof origin+nonce. Never accept any Awoof window by origin alone. Popup response contains only assertion and flow correlation. Include cleanup on success/cancel/re-init and stale attempts. Account context is revalidated server-side after return.
- Existing modal uses div role=dialog without complete focus management. Prefer native dialog, accessible name, Escape/cancel, focus return and properly sized close control. Inputs need associated labels, OTP autocomplete one-time-code/paste support, alert/live errors and honest resend timing. Do not send OTP from effects.
- Browser tests must include signed-out return, account switching, same hostname/different port, forged merchant config, forged window source/nonce, blocked storage/popup fallback, withdrawal, mobile and keyboard. Tests must not pretend a bare source-string assertion proves browser behavior.
