## Required integration contract

- Use publicApiClient for domain preflight and signup request/confirm; an invalid OTP401 must stay in the form and never trigger session refresh/global navigation. The backend remains sole authority. A preflight response's supported boolean is domain support, not mailbox ownership or enrollment.
- Successful preflight now includes server-derived verificationNotice:{version,text}; Astra approved this additive backend contract. Display that wording and an unchecked affirmative checkbox, and send the exact displayed version. Unsupported domain or preflight infrastructure failure must not look verified. Ignore aborted/stale/out-of-order responses after email or institution changes and reset the affirmative action when its displayed version/identity changes. No OTP delivery from effects.
- Freeze a canonical submitted claim object in memory with the server receipt: normalized email, trimmed name, canonical universityId, exact optional matricNumber/null representation, literal consent and notice version. Match backend normalization after its final review. Keep password only in component memory, never URL/browser storage. New request/retry uses explicit user action.
- Request success records challengeId/expiresAt/resendAvailableAt. Confirmation sends that exact receipt and the frozen claims, not current editable form values. Resend must replace the challenge ID with the newly returned receipt and clear old OTP input;429 updates the retry deadline without claiming a new message was sent. A failed or ambiguous resend cannot leave a superseded receipt presented as known-valid; provide honest retry guidance. Do not guess server time-based validity from an arbitrary fixed UI timer.
- Editing identity or going back invalidates the local pending receipt/consent binding. Expired or rejected codes provide an accessible retry path, never a manufactured success. Clear sensitive local pending state on successful completion and abandoned/unmounted flow. Keep password strength consistent with the reviewed backend; no new password policy in this task.
- Extract a shared pure safe same-origin return-path function and use it for login success, signup success and both links. Preserve widget context only through a validated same-origin return path; no account/OTP/password/token in query strings. Treat backend redirect as a fallback, not permission for arbitrary navigation. Integrate Next search-parameter handling without hydration mismatch or missing Suspense boundaries.
- Storage reads/clears should tolerate browser denial; writes must report failure without presenting a persistent signed-in state. Avoid leaving a partial token pair after a failed write. Centralize apiClient token access through these helpers and retain shared-refresh behavior. A response/session/storage failure after account creation must offer ordinary login recovery and must not say the account was rolled back. The popup/iframe fallback itself belongs to the later widget task.
- Refresh completion must remain bound to the session that started it. Current refreshAccessToken reads a token, awaits HTTP and then unconditionally writes the response; it can overwrite a later logout or account switch. The eventual shared-auth task needs an explicit current-session/generation check before persisting/retrying and a controlled late-response test. Do not claim that clearing storage alone cancels already pending refresh work, or that one shared refresh promise can be reused across different accounts.
- Current account state comes from successful authenticated server responses, not decoded JWT fallback. Preserve vendor/admin login behavior and honest loading/error states while removing verification trust from that fallback. Scope the eventual task carefully: shared auth changes need all-role regression coverage.
- Server account identity is not itself effective student eligibility: the legacy /auth/me verificationStatus field remains separate from the new authority. Student verification UI must use the authenticated authoritative status contract after it is implemented, and merchant authorization remains server-side. Do not replace decoded-JWT trust with an equally stale account flag.

### Independent handoff design check

Astra's bounded read-only design review is `/Users/mac/.codex/worktrees/7e93/Awoof/.superpowers/signup-confirmation-handoff-design-review.md`. It supports provider ownership but requires a discriminated result instead of ambiguous void success: completed; not_started(active_session/storage_unavailable); rejected(validation/proof/conflict/other); account_created(session_issuance/storage); outcome_unknown(transport/invalid_response/server); cancelled(aborted/superseded) with observed server outcome not_dispatched/unknown/created. The provider owns safe navigation; the page must not independently navigate after awaiting completion. Results contain no tokens, raw Axios errors/config or submitted claims. A completed result means initiation of validated navigation, not destination-load proof.

The provider must reconcile storage before allocating its operation epoch and before each authority check, copy request primitives rather than relying only on Readonly, and guard provider/page cancellation separately. Own storage commit creates a new generation, so capture and check that adopted snapshot after persistence instead of comparing it to the original signed-out generation. A commit helper mismatch caused by replacement is cancellation, not automatically storage failure; only actual quarantined persistence failure after known valid201 is known-created recovery. Cancellation prevents stale UI/session/navigation but retains whatever server-creation outcome was actually observed. Error serializer fields must be checked at implementation time; malformed/lost201 and generic503 remain unknown, not rollback.

There is an explicit planning gap to resolve before promising stronger cross-tab cancellation: the current signed-out envelope is the constant `{v:1,state:'signed_out'}`, and invalidateToSignedOut advances generation only for active-to-signed-out or forced local invalidation. A remote action ending in the same already-observed marker, including an unobserved active-to-signed-out round trip, is not a durable action epoch. The proposed provider method by itself therefore covers provider-local logout and observed replacement, not every remote action/ABA. Root confirmed this in lib/auth.ts. The future executable plan must either establish a bounded backward-compatible durable action marker with regression evidence, or explicitly limit its guarantee; it must not pretend localStorage is atomic compare-and-swap. No storage-protocol change or such regression has been implemented/approved by this design check, and the active picker task must not absorb it.
