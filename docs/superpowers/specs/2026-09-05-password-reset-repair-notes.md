# Purpose-bound password-reset repair notes

Additional source issue discovered while implementing the audit; not a retrospective renumbering of A01–A18 and not fixed by durable-refresh commit 325b1bc. This document is planning input, not implemented behavior.

## Verified current behavior

- AuthController.forgotPassword selects by case-sensitive email, generates a plain OTP, stores it on users, and attempts email delivery. Optional caller role affects delivery. Success text claims delivery even if the email provider fails; account-existence masking is appropriate, but global unconfigured delivery must not be represented as working.
- verifyResetOTP checks the stored OTP, then returns an ordinary access JWT with hardcoded student role. That token belongs to the ordinary access-token trust domain, although its action proved password recovery only. The OTP is not atomically consumed and optional Redis is not authority.
- resetPassword separately accepts email plus the same OTP, performs SELECT/check, hashes the new password, and UPDATEs password and refresh revocation by user ID. Racing confirmations can reuse the same proof. updatePassword also compares an old password, hashes a new one, then writes by ID without matching the originally checked hash; another password change in between is not detected.
- All four reset UIs (generic, student, vendor, admin) ignore the response resetToken and retain/resubmit the OTP. Role-specific forgot pages preserve an email link, but generic forgot routing needs aligned challenge context. Use publicApiClient for unauthenticated recovery; do not make reset requests depend on a stale access token.

## Bounded repair direction for the executable plan

Use password_reset challenges from the reviewed transaction-capable challenge service. Budget by normalized mailbox across roles so selecting a different form does not reset guesses/sends. Return equivalent challenge response shapes for unknown account, mismatched role and existing account; no account-discovery endpoint. Enforce global/IP limits in addition to subject budgets. New reset challenges should invalidate any older unconsumed reset grant for that account under the same account lock; fresh OTP requests must not preserve a previous authority token accidentally.

On successful OTP confirmation, atomically consume the challenge and create a high-entropy opaque purpose-bound reset grant, storing only its hash and short expiry. Never issue an access or refresh JWT at this step, and never attach a forged/default role. The grant must fail ordinary authenticate middleware and every verification/session endpoint. The final password reset accepts only the grant plus new password, not an email/OTP fallback. UI retains the grant in memory only, not URLs/localStorage/logs, clears it after success or reset, and restarts recovery after refresh/loss. challengeId is non-secret flow correlation, not a substitute for OTP or reset grant.

Bind both challenge and grant to an account credential generation. A narrowly scoped users credential-version trigger on actual password-hash changes ensures any password change (including administrative/direct normal application paths) invalidates older reset proof. Bind normalized account email and reject changed/deleted identity too. Do not store raw password/hash inside challenge JSON. Final reset locks the live account and grant, validates current generation/hash/expiry at database time, consumes the grant, updates password and clears durable refresh fields in one transaction. Compute expensive password hashing outside the lock, then revalidate the checked authority inside the lock. Failed attempts commit challenge budgets; failed proof/password writes roll back consumption. Logged-in updatePassword must use the checked old hash as an update precondition and clear reset grant/refresh authority atomically; a lost race returns conflict/reauthentication rather than overwriting a newer password.

Keep single-active refresh behavior and existing access-token expiry semantics unless a separate reviewed change is justified. No new student onboarding policy, password-policy redesign, provider requests or shared dependency installation in this task. Existing bcrypt behavior and strength validation remain; investigate any maximum-input bound consistently rather than silently changing password rules only on reset.

Remove live use of legacy plain password_reset_otp columns and Redis password_reset entries; a migration may clear deprecated reset proof without backfilling authority. Migration numbering must follow the last committed migration at dispatch, not assume an unreserved number. Align schemas, route documentation and all eight forgot/reset forms using a shared typed transport/controller or component where this reduces duplicated security logic without redesigning layouts. Preserve role-specific login destinations. OTP inputs use one-time-code/autocomplete, numeric input mode, paste-friendly single entry, associated labels and announced errors; no effect-triggered sends.

## Acceptance requirements

Real disposable PostgreSQL tests prove wrong/expired/locked OTP, resend budgets across role/email case changes, concurrent verify (one grant), concurrent reset (one password update), password-change-during-proof race, old grant invalidation on new challenge/password/email change, rollback preserving grant and removing no committed refresh authority incorrectly, deleted user, and no session issuance from OTP verification. HTTP tests prove reset grant cannot authenticate and ordinary access/refresh/student challenge cannot reset; invalid payloads and infrastructure failure never produce success; generic responses do not disclose existence or role. Frontend flow tests cover each role and generic route, correct challengeId/OTP then reset-grant-only transport, no secret URL/storage, restart after lost state, resend and accessible errors. Test mail transport is synthetic only; real provider deliverability remains separately unverified.
