# Merchant integration research notes

Not an executed implementation plan. These notes preserve source/interface observations for the dependent A06/A11/A16 task, after canonical eligibility is reviewed. Paystack feature work stays deferred.

## Existing source and concrete gaps

- api_keys schema is in001_initial_schema.sql around204, rate_limit default100, usage_count0. generateApiKey in payment.controller.ts around525 generates1000request/hour keys; integration dashboard labels requests/hour around691. Current select-latest/revoke-one/insert sequence is nontransactional, uses synchronous PBKDF2 and cannot enforce one active key under concurrency.
- authenticateVendorJwtOrApiKey in middleware/auth.middleware.ts uses SHA256 lookup then async PBKDF2+constant-time check, active vendor/key/expiry, but does not enforce real hourly quota and omits user.deleted_at. Legacy JWT role claim by itself is not sufficient current merchant authority.
- reportTransaction in payment.controller.ts around646 consumes assertion at668 before product/amount/provider validation and before BEGIN around735. A later failure burns proof; simultaneous SELECT/check/UPDATE can redeem twice. The unique vendor payment reference exists but must have idempotent receipt semantics and conflicting-payload rejection, not merely23505 'already used'.
- verification-token.service.ts stores plaintext opaque tokens and uses permanent verified flag, not current proof/grants. It must be replaced/wrapped by one transaction-capable assertion authority, with old unbound tokens invalidated rather than trusted.

## Proposed bounded contract

- Split merchant key lifecycle/quota from payment controller, preserving current key presentation envelope. Generate high-entropy key and async hash before taking short locks; transaction locks live vendor, revokes ALL active prior keys, inserts replacement. Add a database partial unique active-key-per-vendor constraint only after deterministic safe invalidation/diagnostics for legacy duplicates; no plaintext key backfill. Preserve only-once raw-key response.
- Enforce rate_limit as requests/hour, using database time and a serialized counter that survives key rotation (vendor-scoped hourly bucket); otherwise merchant can reset quotas by rotating keys. Increment key lifetime usage_count plus bucket only after successful current authentication; return429 with retry timing on exhaustion. Do not rely on shared IP limit as tenant quota. Validate non-deleted live owner/vendor and key again where required for operation authority. Keep lifecycle/quota lock order explicit and compatible with eligibility operations.
- Add payment-independent POST /api/merchant/verification/exchange with merchant server-key authentication. Body carries opaque token, server-selected expected campaignId, and idempotency key (or standard header); backend resolves vendor from the key, never submitted vendorId. This endpoint requires no product, stock, price, commission or payment gateway.
- Assertion issuance requires authenticated student, current evidence plus current versioned merchant disclosure, active exact-origin widget config, and explicit campaign correlation. Hash assertions at rest; bind subject/evidence/processing and disclosure grants/vendor/origin/purpose/campaign and optional product to the token. Cap assertion lifetime by evidence/grant policy as well as short assertion lifetime. Existing unbound assertions cannot be upgraded from old flags.
- Exchange nonlocking lookup identifies the subject, then uses documented canonical lock order for subject/policy/grants before locking assertion/receipt. Validate live merchant/key within compatible ordering. Atomically consume assertion and save a minimal immutable receipt in one transaction. Wrong vendor/campaign, replay under a different operation, expired/withdrawn/revoked/stale evidence and conflicting idempotency payload must fail without consumption. Same committed idempotency payload returns the stored receipt even after later withdrawal, and creates no new authorization.
- Return only merchant-scoped pseudonymous subject (stable for that merchant, unlinkable across merchants), assurance method/institution/validity and receipt correlation. No global studentID, email/name/registration, account JWT or raw provider data. Browser callback contains only token+flow nonce; merchant server exchange is authority.
- Campaign ID is a merchant-selected correlation boundary, not a promise that Awoof owns coupon rules. Reference connector must select expected campaign on its server (not trust browser submission), exchange token server-side, and atomically allocate/reuse a synthetic coupon with unique(campaign, merchantSubject). This demonstrates prevention of repeated claims with fresh tokens without inventing global pricing or payment rules. Document merchant-owned eligibility thresholds and per-student redemption limits.
- Existing reportTransaction must validate nonsecret request/provider result outside locks as needed, then recheck current product/amount/state and eligibility, consume assertion, record transaction/receipt and stock/savings in ONE DB transaction. No early consume; no external HTTP while holding subject locks. Completed idempotent receipt returns existing result; conflicting vendor payment reference payload fails. Never expand deferred Paystack feature behavior.

## Tests required

Real PostgreSQL: simultaneous rotation leaves exactly one active key; old key denied; quota exact limit and hourly boundary; rotation does not reset quota; revoked/deleted/suspended owner/vendor denied; unrelated merchants independent. Assertion: observed lock contention in simultaneous exchange, withdrawal versus exchange in both commit orders, rollback after consumed token, wrong merchant/campaign/product, expired proof/grant/policy, idempotency identical/conflicting payload, committed retry after withdrawal and fresh-token repeat-coupon claim. Unit transport fixtures must never call Paystack or real merchant/university services.

Browser/integration: exact origin includes port; no shared studentID in iframe/popup/SDK payloads; forged browser success cannot allocate coupon; a synthetic merchant backend successfully exchanges and allocates its voucher. Local success is not VPS/live merchant deployment proof.
