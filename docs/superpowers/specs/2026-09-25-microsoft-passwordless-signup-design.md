# Microsoft passwordless student signup

Status: revision 8, proposed design for owner review; not implemented or deployed. Incorporates the Microsoft/OAuth/NIST guidance reviewed in this task; this is not a certification or compliance claim.

## Goal and approved intent

After successful Microsoft authentication, a new student completes a short Awoof account-creation form without creating a password. Existing linked identities sign in normally. Existing accounts are never silently merged by matching email. School-account control and current enrollment remain separate; signup must not authorize benefits.

Baseline inspected: origin/main 1ced2f5. Current `StudentSsoFlowService.finish` sends all unlinked or revoked identities to a link handoff. The web SSO onboarding page then requires a password session and password reauthentication. The users schema permits a null password hash, but that does not establish that recovery and unlink are safe for passwordless users.

## Selected approach

Extend the existing short-lived, browser-bound unlinked handoff with a dedicated signup-completion operation. Do not create a user in the provider callback, relax account linking, or insert a synthetic password. Preserve existing linking ownership safeguards while extending accepted account-reauthentication proofs to include fresh, purpose-bound Microsoft authentication.

Alternatives rejected: silently creating an account on callback bypasses explicit age and Terms assent; requiring password registration first preserves the current unnecessary friction.

## User flow

1. Email-first discovery and Microsoft authorization remain unchanged.
2. An already-linked active identity uses existing sign-in behavior.
3. An unlinked identity sees “Finish setting up Awoof” with a new-account option and an existing-account sign-in option. Do not disclose account existence during public discovery.
4. New-account completion collects an editable full name, an unchecked 18+ declaration, explicit current Terms acceptance, and separately presented processing consent with its current notice version. Show the server-bound email and institution read-only. No password, phone, date of birth, address or matric number is required for this account-creation flow. Collect matric details later if a specific enrollment method needs them. Explain that enrollment remains pending and an age declaration is not independent age verification.
5. Use validated server-held provider identity, university policy and domain mapping. Do not trust client-submitted issuer, subject, tenant, university or assurance flags. This release requires one mailbox OTP before account creation because Awoof binds the account and its recovery route to that school mailbox, while its Microsoft adapter returns `mailboxVerified: false`. This is an Awoof account-binding choice, not a Microsoft/OIDC requirement or evidence that Microsoft authentication failed. Send only to the normalized, requested school email after it matches the observed identity under the existing strict mailbox-binding rules; missing or mismatched provider email produces an actionable unavailable/restart result, not a guessed address or arbitrary replacement. Explain “Microsoft sign-in succeeded. Confirm this email for your Awoof account and recovery.” Do not repeat signup OTP on ordinary subsequent Microsoft logins. OTP proves mailbox control, not enrollment, MFA or phishing resistance. Do not derive a verified email from `preferred_username` or a tenant ID alone.
6. On success create and link the account atomically, issue the normal session, clear transient browser state and preserve only the existing safe return/claim continuation.
7. An email/account conflict offers secure existing-account login/recovery, without revealing private account details or automatically linking. Previously revoked provider identities cannot become a new user's identity.

## Backend and data contracts

- Add signup context and completion endpoints to the existing student SSO router. Context requires the live handoff proof and returns only necessary form/notice data. Completion is POST, same-origin/CORS guarded, rate-limited and validates a strict versioned request schema.
- Bind enrollment-independent signup to provider+issuer+subject, the exact approved policy/version, browser binding and a one-use secret. Require fresh, unexpired provider authentication and independently adequate mailbox proof. Recheck provider enablement, policy approval, university/domain activity and expiry at commit.
- Preserve existing handoff consume-once protections. Use a dedicated purpose-bound signup challenge linked uniquely to the existing handoff, through an additive migration. Do not rewrite existing consumed attempts or weaken their triggers. Completing signup consumes the handoff under the same lock used by linking, so signup and linking cannot both succeed. No raw provider tokens or secret-bearing URLs/logs.
- In one transaction create users/students, explicit age/Terms assent records, appropriate consent/proof records, provider identity and session state, then consume signup state. Follow the existing lock order; unique email and provider-identity constraints settle concurrent signup races. A failure leaves no partial account or usable duplicate handoff.
- Never write enrollment evidence or set legacy verified flags as a shortcut. Reuse the actual assurance policy; if existing Microsoft school-account assertion prerequisites are unmet, report pending/not-attested honestly.
- Null password hashes are intentional, never replaced with a generated password. Audit every password login, reset, reauthentication and unlink consumer before enabling signup. Password-based calls fail safely for passwordless users.
- Recovery is a release dependency, not follow-up work. For accounts created through this flow, school-mailbox possession alone must never permit password setup/reset or ownership reassignment: institutions may recycle addresses. Require a previously enrolled recovery code plus a fresh mailbox OTP for the independent recovery path described below. Mark these accounts explicitly in server-side credential policy so every legacy reset/setup endpoint enforces this requirement even after an optional password is added; null password alone is not a sufficient policy marker. Reject suspended/deleted accounts, use generic responses, notify the recorded address and revoke sessions and pending action grants on recovery. Never accept the original provider handoff as recovery authorization. Recovery creates no enrollment authority and makes no MFA or NIST AAL claim.
- Passwordless users must not create a password merely to manage sign-in methods. Add purpose-bound fresh Microsoft reauthentication for already-linked identities as specified below; retain password reauthentication for accounts that have passwords. Unlinking the last usable method remains forbidden; an identity under a disabled provider or expired policy does not count as a usable alternative. Revoked identities retain ownership/history. Passkeys are a potential separate follow-up, not silently included or advertised as implemented.
- Ship behind a separate disabled-by-default signup flag. Disabling signup preserves existing Microsoft login/linking; rollback must retain the new account recovery protections and must not restore legacy email-only reset behavior for accounts created by this release.

## Signup challenge, expiry and retry contract

- Existing handoffs have a ten-minute lifetime. The signup challenge, verified OTP proof and all resends are capped by that original expiry; nothing silently extends provider authentication. Display the remaining time and provide a clear restart action on expiry.
- Generate a cryptographically random six-digit OTP. Store only a keyed digest bound to challenge ID, intended mailbox and generation; do not log codes. A code expires after five minutes or at handoff expiry, whichever is sooner. Only the latest generation is usable.
- Permit at most five failed code checks across the entire challenge, at most three sends including the initial send, and at least sixty seconds between sends. Resending does not reset failures. Apply existing account/IP abuse controls as additional limits, never relax stricter existing limits. Exhaustion requires a fresh Microsoft attempt; cross-attempt throttles prevent resetting abuse budgets by restarting.
- Verify OTP separately from account creation, recording a challenge-bound proof usable only until handoff expiry. A successful OTP does not create an account, accept Terms, authenticate the user or change eligibility. Sending mail happens outside database locks with reserved send quotas; delivery errors remain retryable within those quotas.
- Completion requires the same browser binding, handoff secret and verified challenge plus current explicit assent. Recheck all expiry and policy conditions inside the transaction after acquiring locks. Lock ordering and unique constraints must cover competing signup, linking, revocation and recovery requests; database integration tests must exercise actual interleavings.
- A repeated submit cannot create another account or issue another session from a consumed handoff. If the transaction committed but the response was lost, show a neutral restart-sign-in message. A fresh Microsoft sign-in then finds the linked identity and signs in normally. Do not replay tokens or refresh consumed handoffs for convenience.
- An expired flow clears sensitive transient state. Non-secret profile text can remain in memory for convenience, but a fresh attempt must rebind its identity and require fresh explicit assent; never carry an old OTP proof or checked consent into a different identity.

## Fresh Microsoft reauthentication for sensitive actions

- This is a distinct purpose-bound flow, not reuse of signup/login callback results. Start only from an active Awoof student session and an existing non-revoked Microsoft identity owned by that user. Bind the attempt to user ID, current session ID, identity ID/version, requested operation and target identity where applicable.
- Use Authorization Code + PKCE S256, exact registered redirects, state, nonce and server-side signature/issuer/audience/time validation. Request fresh authentication with `max_age=0`. Require numeric `auth_time >= attempt.started_at - 60 seconds` and `auth_time <= server_now + 60 seconds`; the attempt itself expires five minutes after creation and is single-use. An authentication timestamp merely within the last five minutes is insufficient if it predates this attempt beyond clock tolerance. A prompt alone or a newly issued token is not proof of fresh authentication. If Microsoft cannot supply the required claim in a live test, do not silently accept ordinary SSO as reauthentication; this release gate remains unmet.
- Returned issuer/subject and tenant/object identity must match the stored linked identity; an account-picker switch must fail safely without changing the current Awoof account or session. Recheck provider enablement, policy validity, identity revocation and active session at callback and sensitive-action commit.
- Mint a one-use, five-minute action grant bound to the verified provider identity and operation, distinct from password-bound grants. Do not make null password hashes satisfy existing password grants. Reauthentication must not create/link identities, write enrollment evidence or issue an unrelated login session.
- For adding another identity, prove the existing account with this action grant and separately prove the new identity through the normal linking handoff. For unlink, bind the grant to the exact removal target and enforce the remaining usable-method check transactionally. Revocation, session replacement, account suspension or policy invalidation cancels outstanding grants.
- When the provider or policy is unavailable, show the separately tested account-recovery route; do not bypass action proof. Optional password setup remains recovery, not a prerequisite for normal passwordless account management.

## Policy expiry and operational recovery

The live identity-only pilot was observed configured to expire on 25 October 2026; recheck runtime policy before release. Before enabling new passwordless signup, prove recovery-code-plus-mailbox first-password setup end to end with Microsoft disabled and with the pilot policy expired. No automatic policy extension or approval bypass is permitted.

After successful signup and its requested continuation, offer “Save your recovery code” as an optional account-security task, outside the core signup journey. Do not interrupt a claim continuation or require a second Microsoft authentication merely to finish signup. Explicitly choosing initial code setup requires fresh purpose-bound account reauthentication. This release adds one active, cryptographically random recovery code containing at least 128 bits of entropy per account. Store only a keyed digest with account ID and generation. Never email it or log it. Display plaintext only in the generation response; do not persist it in browser storage. Users may skip setup but must see that recovery is not configured and that losing their school sign-in may prevent account access. Do not claim universal recoverability.

Recovery-code enrollment and replacement use an explicit pending/active lifecycle:

**Explicit UX tradeoff:** this design requires two fresh authentication steps for code setup: one before generation and another before activation. They authorize distinct operations; the implementation plan must budget for both, not silently reuse a consumed grant. Before starting, explain “Confirm your identity, save your code, then confirm your identity again to activate it.” Show progress, expiry and a safe cancel/restart action. Cancellation or expiry must preserve any existing active code. Keep the task optional and outside signup/claim continuation, and test both authentication transitions, cancellation and expiry in the browser. This is a deliberate design choice, not a claim that Microsoft requires two prompts; simplifying it would require a separately reviewed authorization contract.

- Generate a pending code only after fresh purpose-bound reauthentication. Its digest and confirmation challenge expire after ten minutes. Require the user to re-enter the code to confirm possession before activation; a checkbox alone is insufficient. Pending codes cannot recover an account and do not replace an active code. Never display plaintext again. A lost generation response leaves the active code intact; a new freshly reauthenticated generation invalidates only the preceding pending code. Scrub expired pending secrets under the transient cleanup schedule.
- Generation consumes a one-use `recovery_code_generate` grant. Activation requires a separate, unconsumed `recovery_code_activate` grant issued after fresh reauthentication, valid for five minutes and bound to the exact pending generation, user, current session ID and credential generation. Do not reuse the consumed generation grant. The pending code's ten-minute expiry is absolute: renewed reauthentication never extends it. If the activation grant expires while the pending code remains live, obtain a fresh activation grant; if the code expires, restart generation. For replacement, activation also requires a fresh proof of the still-active old code, bound to that same operation.
- Under the account lock, activation rechecks the session, credential generation, active-account state, pending generation/expiry and all action proofs before consuming the activation grant and committing. Logout, session replacement, password change, compromise recovery, or revocation of the identity used for proof invalidates pending activation state. Subsequent sign-in cannot revive it: restart generation without changing any existing active recovery code. Test each invalidation racing activation so an obsolete session cannot activate a code.
- When an active code exists, generating and activating its replacement requires both fresh account reauthentication and proof of the existing active code, bound to that exact code generation and replacement operation. Activation atomically rechecks both proofs, confirms possession of the pending code and swaps active generations. Serialize against recovery, cancellation and other replacement attempts. Merely controlling Microsoft or the Awoof session must not invalidate an active recovery code. Apply this protection to explicit recovery-code removal too.
- If the existing active code is lost, refuse self-service replacement in this release. Do not fall back to Microsoft authentication or mailbox OTP alone. Explain that ordinary available login methods still work, but recovery-code replacement needs a separately designed and approved lost-code process; support must not bypass this rule. Notify the recorded address on activation, replacement or removal without including credentials.
- The protection preserves an already-enrolled code against provider-only replacement. It does not protect initial enrollment when no independent recovery proof exists, or make a compromised Microsoft identity safe. Describe that boundary accurately.

Independent recovery requires the saved code and an OTP to the already-bound mailbox, both bound to one ten-minute recovery attempt. OTP expiry, resend and failure limits use the signup limits above; apply cross-attempt account/IP limits and generic responses to code checks as well. Consume the code only in the successful password-setup transaction, invalidate competing attempts and all existing sessions/action grants, and require ordinary login afterward. Do not permit email changes or identity reassignment through this endpoint. A reassigned-mailbox holder without the saved code cannot recover the old account. A user with neither usable provider access nor both recovery proofs receives support guidance, not an ownership bypass.

Successful recovery atomically clears the consumed code and any pending replacements and marks recovery as unconfigured. Do not automatically issue or email a replacement. On the next password login, show a persistent, non-blocking “Save a new recovery code” action and explain that the previous code was used. Re-enrollment following recovery requires fresh password reauthentication against the current password and current credential generation; a retained Microsoft identity cannot perform this first re-enrollment by itself. Persist this password-proof restriction independently of the password hash: a legitimate password change invalidates outstanding grants and pending code state but retains the restriction, and the new current password can authorize a restarted setup. Clear the restriction only when a new code is confirmed active. This remains outside the core signup journey. Users who decline are explicitly shown as lacking configured recovery; the consumed code never becomes valid again.

Recovery distinguishes two explicit purposes, bound to the server-held recovery attempt and confirmed before completion:

- **Lost access, no suspected compromise:** establish the optional password and revoke existing sessions/action grants, but retain linked provider identities. Explain that those identities will still be able to sign in if their provider and policy permit it. This path restores access; it does not contain provider compromise.
- **Suspected sign-in compromise:** show an explicit warning that completion will disconnect all linked external sign-in identities. In the same transaction as password setup and recovery-code consumption, revoke all external login identities, revoke school-account assertions derived from those identities, invalidate all sessions, reauthentication grants, and pending login/link/signup/recovery state associated with the account or those identities. Retain ownership tombstones so another account cannot claim the revoked identities. Independent enrollment evidence is not changed merely by this login recovery operation. The new password is the surviving usable method; its ordinary login is required after commit. No external identity is automatically reactivated: relinking requires fresh proof of the recovered Awoof account and provider identity through the existing secure linking flow.

Both purposes require the same recovery code and mailbox proof; neither may be selected using only email possession. Serialize recovery against in-flight provider callback/session issuance, linking and password changes using the account lock and credential/session generation. A provider login racing compromise recovery must either finish before recovery and have its session invalidated, or observe the new generation/revocation and fail. UI warnings must advise securing the Microsoft account and mailbox too; Awoof cannot revoke Microsoft's own sessions or prevent access to a compromised inbox. Security notifications must contain no recovery code or reset credential.

**Pilot limitation requiring owner acceptance before release:** this fallback is independent of Microsoft's availability and Awoof's institution-login policy, but not independent of school-mailbox availability. A graduate who loses both provider access and the mailbox cannot use it, even with a saved recovery code. Display this limitation when offering recovery setup. Do not advertise lifelong access or guaranteed recovery. A verified personal recovery address or passkey-based recovery would require a separate design and approval; neither is silently added here. If the owner does not accept this pilot limitation, keep passwordless signup disabled until the expanded recovery design is approved and implemented.

Login UI must explain the recovery alternative when school sign-in is unavailable without disclosing whether an email has an account. Users missing required recovery proofs may contact the monitored support channel; do not promise recovery or allow support to assign ownership based solely on a matching name, matric number, email possession or screenshot. Adding a separately verified personal recovery email is a distinct future design, not implicitly included here.

Disabling only the new-signup flag must preserve existing linked sign-in. Disabling Microsoft itself can prevent provider sign-in; the tested independent recovery route is required for that case. These are separate rollback operations.

## Transient retention and cleanup

- On successful OTP verification, immediately clear its digest; retain only the challenge-bound proof until completion or expiry. Resend immediately invalidates the old digest. On completion, cancellation or failure-budget exhaustion, immediately scrub transient OTP digests, encrypted provider observations and verifier/nonce material no longer needed. Never retain raw tokens.
- Run cleanup at least every fifteen minutes. For abandoned/expired signup, reauthentication and recovery attempts, scrub remaining secret digests and encrypted payloads no later than one hour after expiry. Delete secret-free transient rows within seven days after terminalization or expiry. Retain only minimal IDs, outcomes and timestamps needed for those tombstones; durable account identities and legal assent records follow their separate reviewed retention policies.
- Consumed action grants lose their secret digest immediately; expired grants are scrubbed within one hour and tombstones deleted within seven days. Persistent recovery-code digests are credential records, not transient attempts: retain an active digest until consumed, replaced or account deletion, clear it immediately on those events, and retain any secret-free generation tombstone for at most seven days. Do not extend these rules to unrelated audit/legal records.
- Extend the existing cleanup job and schema constraints together. Test cleanup racing verification/completion and ensure deleting tombstones never enables replay. Alert on failed cleanup runs and oldest unscrubbed expired state exceeding one hour; production enablement requires demonstrated alert delivery, not merely local logs.
- These deadlines concern the live database. Backups and external email delivery systems have separate retention; do not claim immediate global erasure. Assess public documentation impact and obtain review before publishing new retention commitments.

## Frontend and public documentation

Extend existing complete/onboarding routes and shared auth shell rather than creating competing flows. Update typed response parsers and tests. Prevent double submissions and stale-session writes; preserve entered non-secret details after retryable failures. A stale notice requires fresh assent, never silent acceptance.

Use accessible labels, error focus, keyboard navigation and responsive layout. Update help/trust/privacy/developer disclosures only where behavior or collected data changes. Record source/test evidence and pending production validation; do not claim university partnership, current enrollment or independently verified age.

## Acceptance and release gates

Additional required cases: old OTP after resend; exhausted failure/send budgets across resends and restarts; email delivery failure; handoff expiry after OTP success; signup racing existing-account linking; commit-success/response-loss followed by fresh provider login; null-password recovery with provider disabled or approval expired; suspended/deleted account recovery denial; alternative identity with expired policy not counted as usable; and no silent migration of school-account proof into enrollment evidence.

Fresh-reauthentication cases: missing/stale/future `auth_time`; different Microsoft account; wrong issuer/audience/nonce; session switch; revoked identity; operation/target substitution; consumed or expired grant; provider/policy disabled between callback and action; null-password grant confusion; successful passwordless account management without password creation; and concurrent last-method removals. Verify live Microsoft freshness behavior separately from mocks before enabling passwordless signup.

Revision-4 cases: an authentication timestamp five minutes old but preceding attempt creation is rejected; exact clock-skew boundaries; reassigned mailbox without recovery code; email-only legacy reset bypass before and after password setup; missing/replaced/consumed recovery code; concurrent code consumption; recovery setup skipped or response lost; signup disabled without removing recovery protections; immediate scrubbing and one-hour/seven-day cleanup boundaries; cleanup races and alert delivery. Recovery-code generation, reauthentication and recovery are explicit implementation scope, not assumed existing capabilities.

Revision-5 cases: recovery purpose cannot be substituted after proof; lost-access recovery clearly preserves linked identities; compromise recovery atomically revokes every external identity and derived school assertion; concurrent provider callbacks cannot issue surviving sessions after recovery; rollback leaves neither partial revocations nor a consumed recovery code; revoked identities cannot migrate to another account or silently reactivate; new password remains usable while independent enrollment state remains unchanged; unavailable school mailbox fails closed despite a valid code; optional recovery setup does not interrupt signup or safe claim continuation. Record explicit owner acceptance of the mailbox-availability limitation before enabling signup.

Revision-6 cases: provider-only replacement/removal of an active code is denied; replacement binds the old code generation; pending codes cannot recover; possession confirmation is mandatory; lost generation responses preserve the active code; replacement/recovery races yield one valid outcome; expired pending codes are scrubbed; lost-active-code replacement fails without an alternative bypass; successful recovery clears pending/active codes and marks recovery unconfigured; next login displays the setup action; provider-only post-recovery re-enrollment is denied; fresh recovery-password proof enables re-enrollment; consumed codes never reactivate. Verify safe retry behavior when activation succeeds but its response is lost: the user already holds the confirmed code, and authenticated status reveals only generation/status, never plaintext.

Revision-7 cases: consumed generation grant cannot activate a code; activation grant is purpose/session/credential/pending-generation bound; expired activation proof requires fresh proof without extending pending-code expiry; logout/session replacement/password change/identity revocation/recovery racing activation fails safely; old pending state cannot revive after sign-in; legitimate post-recovery password change retains the password-proof restriction but permits setup with fresh current-password proof; provider-only setup remains denied until confirmed activation clears that restriction.

## Standards references and limits

- [OAuth 2.0 Security BCP, RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html): authorization-flow protections and redirect/token handling. The implementation plan must map controls to source and tests rather than treating the citation as proof of compliance.
- [Microsoft ID token claims](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference): stable subject identifiers versus mutable email/username attributes. Authentication, mailbox control and student enrollment remain distinct.
- [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html): email is not an out-of-band authenticator. Mailbox confirmation and recovery must be described by their actual purpose; no NIST assurance level, MFA or phishing-resistance claim is implied for this design.

Run PostgreSQL integration tests against real constraints, frontend unit/browser tests for the full completion flow, type/lint/build checks and documentation-link checks. Test backend-first deployment and old/new frontend compatibility. Do not patch running production code directly.

Before production signup enablement, verify cleanup covers new state, record a rollback procedure, and complete local/staging browser tests. A real Microsoft test then requires the user to enter credentials/MFA and accept their own legal declarations. Verify callback, account/session creation, reload persistence, subsequent Microsoft login and pending enrollment separately. A redirect alone is not end-to-end success.
