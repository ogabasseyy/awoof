# Authenticated verification flow implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Wire approved email assurance and strict enrollment decisions to the signed-in student, retire public identity-grant bypasses and expose honest availability. No verification endpoint may create/select another account from request identity fields or issue a login session.

**Architecture:** Small authenticated flow and provider-adapter services compose the reviewed transaction-capable eligibility authority. Request email/provider transport happens outside transactions; confirmation/application rechecks current identity, policy and consent. Public endpoints expose availability only, not student status or eligibility claims.

**Prerequisites:** Astra-approved eligibility-authority and proof-bound-signup tasks; reconcile exact interfaces before dispatch. This plan is initially a draft for independent plan review. Dispatch one implementation task at a time, with its own BASE/report/Astra gate.

**Stack:** Existing Express/TypeScript/Zod/pg/Axios/node:test. No new dependency or framework upgrade.

## Global constraints

- Work only in /Users/mac/Downloads/Awoof/.worktrees/verification-remediation. Terra implements, Astra reviews. No subagents, concurrent implementation workers, dependency installs, shared node_modules changes, production/provider requests, push/merge/deploy or real personal data.
- Approved student-email OTP is sufficient first-line assurance on explicitly approved student domains; default90 days. No generic academic suffix/directory inference, permanent-flag authorization, assumed consent, fallback provider identity or automatic domain/origin approval.
- User identity comes only from authenticated userId and fresh locked DB state, never studentEmail/name/phone/studentId in request bodies. JWT role alone is not live role authority. Infrastructure failures never become successful or negative enrollment evidence.
- Preserve common user -> student -> institution(s sorted) -> state -> consent -> challenge -> assertion lock order. Failure statuses that consume guesses return from the transaction before HTTP errors are thrown. No delivery/provider HTTP or CPU-heavy hashing while locks are held.
- Disclosure endpoints are distinct transaction entrypoints: acquire the full student/merchant-owner participant-user set in UUID order before any context/grant lock. Do not call a disclosure-qualified authority read after an ordinary eligibility read/proof write in the same transaction unless all participants were locked at entry. Owner withdrawal uses its reviewed ownership-only path, including inactive/missing-current-profile cases and sorted historical/current institutions; do not add an active-only controller precheck that blocks revocation.
- Signup is a separate reviewed task. Ordinary vendor mailbox/password-reset migration, admin policy/profile UI, merchant exchange/benefit consumers and widget UI remain dependent work. Paystack features/manual-review product decisions remain deferred.

### Task 2: Strict enrollment adapter and honest configured availability

**Owned files:** Replace registration-lookup.service.ts with a strict typed adapter and add .test.ts; modify verification-flow.service.ts/controller/route only for authenticated registration orchestration, verification-orchestrator.service.ts only truthful registration availability. Add testing/postgres/enrollment-flow.integration.ts and HTTP tests. Own HANDOVER versioned provider contract and these task checkboxes. Minimal new provider-config parsing helper allowed; do not change reviewed authority/schema/consent rules without reporting the conflict.

The server-configured active registration adapter must explicitly opt into a known contract version in its api_config; a generic URL or default seed method alone is not configured enrollment. Define/document version `awoof.enrollment.v1`. Exact response union: `{schemaVersion:'awoof.enrollment.v1',outcome:'unknown'}`; verified additionally has provider-attested email, registrationNumber and validUntil; denied additionally has provider-attested email. Fields have strict runtime types and bounds; validity is an actual finite future timestamp. Non-boolean flags, a name, a studentData object, HTTP404, missing email, caller-email fallback, unrecognized shape/version, timeout, malformed JSON and transport errors are unknown/unavailable, never positive or authoritative negative. The internal adapter supplies ENROLLMENT_SOURCE; raw response/caller source never passes through as trusted metadata.

Authenticated POST /verification/registration accepts strict `{ registrationNumber, processingGrantId }` only. BeginEnrollmentCheck transaction produces an immutable proven-mailbox snapshot; after commit call the configured adapter with that account email and requested registration number, then applyEnrollmentDecision in a new transaction. No request may replace university/email/name/subject. Positive and negative emails must match the proven current mailbox. Returned registration number must correspond to the requested identifier under the institution's explicit normalization, never an unconfigured guess. Snapshot revalidation, denial precedence and generation single-application remain in the authority. API returns only effective eligibility and a bounded unknown/unavailable reason, never provider blobs or JWTs.

Endpoint configuration is server-side, not a URL in the request. Follow current official Axios request-config documentation when implementing timeout/content-size/no-redirect bounds and validate HTTPS endpoint/userinfo rules; tests use injected transport, not real university HTTP. Do not silently configure an institution or claim actual provider compatibility. If safe destination validation needs a product/network exception, report it rather than inventing a live allowlist. Availability checks exactly the same supported-version/active-policy/endpoint/normalization criteria as execution; portal/WhatsApp remain unavailable.

**Transport reference check, 2026-09-05:** The successful official-document fetch supersedes the earlier failed attempt recorded in scratch. Axios supports explicit timeout, AbortSignal, response/request size limits, `maxRedirects:0`, custom HTTPS agent/lookup and `proxy:false`; do not spread provider JSON into arbitrary Axios configuration or log Axios errors with credentials. [Axios request configuration](https://axios-http.com/docs/req_config).

Endpoint syntax alone is insufficient: use explicitly configured destinations, validate resolved IPv4/IPv6 addresses and prevent redirect/DNS changes from reaching internal services. This is an Awoof implementation requirement informed by the documented DNS-pinning and allowlist risks, not evidence of live network protection.
