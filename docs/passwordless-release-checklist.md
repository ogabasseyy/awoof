# Passwordless student sign-in release checklist

Status: **not approved for activation**. This checklist describes the release gate for source changes on this branch; it is not deployment evidence.

## Backend-first rollout and rollback

- [ ] Apply migrations 069--083 and deploy the backend before any web client that invokes the passwordless routes. Migration 075 replaces 072's immutable-binding trigger so activation can scrub pending-only bindings; without it every recovery-code activation fails. Migration 076 extends that scrub to revoked rows (cancel, supersede, remove, recovery consumption, expiry cleanup); without it those terminalizations fail. Migration 077 drops the legacy reauth-grant digest uniqueness so recovery can scrub multiple retained rows; without it a second retained row aborts the recovery transaction. Migration 078 adds the reauth processing claim so duplicate provider callbacks redeem once; without it a duplicate redemption can fail the winner's attempt. Migration 079 persists post-recovery session binding so legacy sid-less tokens stay revoked after re-enrollment; without it an attacker's pre-recovery token resurrects. Migration 080 adds the recovery-attempt idempotency key so cooldown retries rebind only with the original start's binding; without it `/account-recovery/start` fails with a missing-column database error. Migration 081 initializes a database-time SSO-attempt fence for existing users and advances it on recovery so pre-boundary provider attempts cannot establish sessions afterward, including alias-mailbox attempts. Migration 082 scrubs cooldown idempotency keys when attempts leave the pending state or expire. Migration 083 persists encrypted recovery OTP delivery jobs atomically with attempts/challenges.
- [ ] For migration 083, roll out the migration before new backend replicas and drain old backend replicas before accepting new recovery starts. Old replicas neither write nor process outbox rows, so mixed-version rollout is not a seamless delivery guarantee. Configure `STUDENT_ACCOUNT_RECOVERY_OTP_ENCRYPTION_KEY` on every backend replica before enabling starts; it must be canonical base64 for 32 random bytes, distinct from other application keys, and identical across replicas/workers. During rotation, configure `STUDENT_ACCOUNT_RECOVERY_OTP_PREVIOUS_ENCRYPTION_KEY` on every worker and retain it at least through the maximum five-minute OTP lifetime plus queue/clock margin. Do not retire an old key while rows encrypted under its key ID remain deliverable.
- [ ] Recovery OTP delivery is bounded at-least-once using the same OTP until challenge expiry or retry-budget exhaustion. A timeout can happen after provider acceptance, so duplicate emails are possible; exactly-once delivery is not promised. Verify restart/lease recovery, same-code retry, terminal-state suppression, and immediate ciphertext scrubbing in the outbox integration suite before rollout.
- [ ] Before applying migration 081, quiesce SSO starts/callbacks and account-recovery completion on pre-migration backend replicas; keep those operations blocked until the migration is applied and every serving backend checks the fence. A migration-time watermark cannot constrain old code that creates an attempt after backfill or completes recovery without advancing/checking it. The fence rejects attempts created before its timestamp; it does not revoke active sessions.
- [ ] Keep student SSO signup disabled until every gate below is evidenced. Disabled signup must return the documented bounded response; existing account sign-in and owner recovery remain separately controlled.
- [ ] Exercise an old web client against the new backend before enabling signup. It must continue normal supported sign-in without interpreting passwordless payloads as eligibility.
- [ ] If rolling back the web client, keep the new backend credential protections and migrations in place. Once passwordless accounts exist, do not restore a legacy email-only recovery binary or path.
- [ ] Confirm the production cleanup job invokes `sso:cleanup:prod` at least every 15 minutes and that its runtime has the credential keys and database access it needs.
- [ ] Keep cleanup within its per-table 500-row batches. A larger backlog drains on later runs; the overdue counts must be monitored and any count above zero is an alert, not a green cleanup result. Ordinary SSO login tombstones retain only SHA-256 digests of the one-use finish and browser-binding secrets so the same browser can safely retry a lost response; cleanup scrubs those digests at attempt expiry on the next scheduled run and keeps the non-secret replay tombstone for seven days. The one-hour threshold is an overdue-cleanup alert, not an added retention period. Confirm the cleanup deadline and alert delivery with the production scheduler before activation. Other passwordless transient secrets are scrubbed by their terminal transitions or expiry cleanup.
- [ ] Configure the production mailer (`BREVO_API_KEY`) and valid shared outbox key before advertising mailbox account recovery. Without either, `/account-recovery/start` returns 503 by design; `/account-recovery/verify` and `/account-recovery/complete` stay usable for already-delivered OTPs, and recovery-code management (key-gated only) is unaffected.
- [ ] Before enabling recovery codes, record owner-approved continuity evidence for the effective `STUDENT_ACCOUNT_RECOVERY_CODE_KEY`: a code issued before a rolling deployment still verifies afterward, and a code issued after deployment also verifies. Do not record or publish key values. For a K1-to-K2 rotation, use two completed rolling deployments: stage 1 keeps the effective write key at K1 and sets `STUDENT_ACCOUNT_RECOVERY_PREVIOUS_CODE_KEY=K2`, so every replica still writes K1 but can verify both K1 and K2; stage 2 promotes `STUDENT_ACCOUNT_RECOVERY_CODE_KEY=K2` and sets the previous key to K1, so every replica writes K2 and verifies both. Only remove K1 from the previous-key setting after every K1-enrolled code has been replaced or revoked. If introducing a dedicated key, treat the existing effective key as K1 and follow the same verify-only-before-promotion sequence. An unplanned key change can make active recovery codes unusable; never present a successful build or configured variable as continuity proof.
- [ ] If the dedicated recovery-code key is introduced while codes were issued under the retained SSO attempt key, keep that retained key as the previous verification key until those codes are re-enrolled. A deployment must not drop the fallback merely because the dedicated key is present.

## Owner-operated evidence required before activation

- [ ] The owner accepts the limitation: mailbox availability and a school login do not by themselves prove current enrollment, and recovery requires the documented proofs.
- [ ] Securely inspect the existing Azure app/tenant configuration, redirect URLs, credentials, consent configuration, and environment separation; do not paste secrets into this document or tickets.
- [ ] Run a user-operated Microsoft test including MFA/consent where applicable. Capture only safe evidence that `auth_time` is present and fresh enough for the flow.
- [ ] Demonstrate disabled-signup behavior, approved signup, session persistence after reload, a later normal login, and a denied-benefit result without current enrollment evidence.
- [ ] Demonstrate a real cleanup failure and overdue-expired-state alert reaching the accountable owner. Local stderr/exit status is alertable signal only; alert delivery is still pending.

## Documentation-impact checklist

1. Affected pages: `/help`, `/trust`, `/privacy`, `/developers`, partner integration copy, OpenAPI, and this internal trust inventory.
2. Public wording must distinguish source/tests from deployed/enabled behavior; it must not claim a university partnership, current-enrollment proof from login, MFA, or universal recovery.
3. Evidence is source migrations 069--083, cleanup command output/tests, route/OpenAPI contracts, and this gate list. Deployment, provider, merchant, and alert-delivery evidence remain pending.
4. Before release, check rendered links/contact destinations, headings, keyboard navigation, labels, and mobile layout.
5. No new legal commitment is made here. Any new data-sharing, retention-policy, vulnerability-disclosure, or response-time commitment needs owner/legal/operations approval.
